## §1 Purpose and boundary

A page fault is the processor telling the kernel that a memory access cannot be completed with the page tables as they currently stand. This mechanism owns everything between that trap and one of two endings: the page tables are changed so the instruction can be run again, or the access is refused and the thread is sent a signal.

The reason it deserves a specification of its own is that it is the only place in the kernel where the hardware asks a question and blocks a thread until software answers. Every other memory operation is software choosing to act. This one is software being interrupted mid instruction and having to leave the machine in a state where that exact instruction can be retried and produce a different result. The restart is the property everything else here is built around.

What it is not responsible for:

- Choosing which pages to evict, and writing them out. That is the `reclaim` blueprint. This one asks for a page and takes what it is given.
- Deciding where a mapping lives and what flags it has. That is the `mmap` blueprint. This one reads the VMA and never creates one, with the single exception of growing a stack.
- The shape of the page tables themselves, and the rules for walking them. That is the `page-tables` blueprint.
- Reading file content into the page cache. That is the `page-cache` blueprint. This one calls into it and waits.
- What happens when memory runs out. That is the `oom` blueprint. This one hands the fault over and does not come back.
- The scheduler decision that runs another thread while this one waits on a disk read. That is the `scheduler` blueprint.

## §3 Algorithms

Numbered from the trap. Steps 1 to 5 are architecture specific and steps 6 onwards are not, and the boundary between them is `handle_mm_fault` [page-fault-R11], which is the same function on every architecture Linux supports.

1. The processor pushes an error code and traps to vector 14, having already put the faulting address in the CR2 register. The kernel entry point is `exc_page_fault` [page-fault-R1]. Reading CR2 is the first thing it does, before anything that could itself fault, because a nested fault would overwrite the register and the original address would be gone.

2. Decode the error code [page-fault-R2]. Seven bits, and the four that decide the path are: was the page present, was this a write, was the access from user mode, and was it an instruction fetch. A fault where the page was present is a permission problem. A fault where it was not present is a missing translation. These are different problems with different endings.

3. Fire the tracepoints [page-fault-R24], one for a fault taken in user mode and one for a fault taken in kernel mode. This happens before any decision, so a trace shows every fault including the ones that turn out to be a kernel bug.

4. Split on the address [page-fault-R3]. An address in the kernel half is either a vmalloc mapping that needs synchronising into this process's page tables or a bug, and either way it does not go through the VMA machinery. Everything below is the user address path [page-fault-R4].

5. Refuse anything that arrived in the wrong context. A fault taken while the kernel was holding a spinlock, or inside an interrupt handler, cannot be resolved, because resolving one can sleep. The handler looks for an entry in the exception table covering the faulting instruction [page-fault-R23]. A fault inside `copy_from_user` is expected and has such an entry, and it returns an error to the caller. A fault anywhere else in that state is a bug and becomes an oops [page-fault-R21].

6. Find the VMA covering the address, and try the cheap way first. `lock_vma_under_rcu` [page-fault-R5] looks the VMA up under RCU and takes a lock on that one VMA rather than on the whole address space, which lets faults on different mappings in the same process proceed at the same time. When that does not work, fall back to `lock_mm_and_find_vma` [page-fault-R6], which takes the mmap lock for read and searches the tree. Failing to find a VMA at all ends the fault with SIGSEGV.

7. Check the access against the VMA flags [page-fault-R7]. A write to a mapping without write permission, or an instruction fetch from a mapping without execute permission, ends here with SIGSEGV. This check is against the VMA and not against the page table entry, and that difference is what makes copy on write possible: the VMA says writable, the page table entry says read only, and the two disagreeing on purpose is the signal that a copy is needed.

8. Call `handle_mm_fault` [page-fault-R11]. Everything from here is architecture independent. The fault flags travel with the call, and the one that shapes the rest of the path is `FAULT_FLAG_ALLOW_RETRY` [page-fault-R10], which grants permission to give up, drop the lock and have the caller start the whole fault again.

9. Walk the page tables downwards [page-fault-R12], allocating any level that is missing as you go. A first touch of a fresh mapping can allocate three levels of page table before it gets anywhere near the page the program asked for. With transparent huge pages built in, the walk can stop at the pmd level and be answered there [page-fault-R25] rather than descending to a pte at all.

10. Look at the page table entry and dispatch [page-fault-R13]. This is the four way split in the picture, and every branch of it ends by installing an entry:

    - The entry is empty and the VMA has no backing file, so this is anonymous memory [page-fault-R14]. A read gets the shared zero page, which costs nothing and is read only, so the next write to it faults again. A write allocates a folio, zeroes it, and maps it.
    - The entry is empty and the VMA has a backing file, so the content has to come from the page cache. The mapping's own fault operation is called [page-fault-R19], which for an ordinary file is `filemap_fault` [page-fault-R18]. A private mapping being written to takes a longer route and copies what it read [page-fault-R16]. The entry is installed by `finish_fault` [page-fault-R17].
    - The entry is not empty but is not a present translation either, so it holds a swap entry [page-fault-R15]. The page has to be read back from storage, and the fault sleeps until it arrives. This is the one branch that reliably counts as a major fault.
    - The entry is present and read only and this was a write. Either the VMA is genuinely read only, which was already refused at step 7, or this is copy on write, which allocates a new folio, copies the old content into it, and replaces the entry.

11. Install the entry under the page table lock, and check under that lock that nothing changed while it was not held. Another CPU faulting on the same address at the same time can have finished the same work already, and the correct response to finding that is to drop what this fault built and use what is there. A fault losing a race is a normal outcome and not an error.

12. Return a `vm_fault_t` [page-fault-R20]. The architecture code turns it back into one of the endings: return to userspace and let the instruction run again, send a signal, or hand the whole thing to the out of memory killer [page-fault-R26]. A return of `VM_FAULT_RETRY` means nothing was fixed, the lock was dropped, and the fault has to be taken from the top.

13. Account for it [page-fault-R28]. A fault resolved without touching storage is minor, one that waited on storage is major, and both counts are visible per process [page-fault-R27].

## §4 Invariants, locking and context

### §4a Invariants

1. The faulting instruction is restartable, so the fault handler leaves no state that would make running it a second time behave differently from running it once. [unchecked]
2. CR2 is read before any code that can itself fault, because a nested fault overwrites it. [checked: the entry point reads it first, and a fault before that read loses the address]
3. A VMA found under the per VMA lock is still the VMA covering this address at the moment its lock is held, or the lookup fails and the fault falls back to the mmap lock. [unchecked]
4. A page table entry is only written while the page table lock covering it is held. [unchecked]
5. Two CPUs faulting on the same address install at most one folio between them, and the loser frees what it built. [unchecked]
6. A fault that returns VM_FAULT_RETRY holds no mmap lock and no per VMA lock when it returns. [unchecked]
7. Every folio installed into a page table carries a reference for that mapping, taken before the entry is written and dropped when it is torn down. [unchecked]
8. A fault taken in a context that cannot sleep either resolves without sleeping or is covered by the exception table. [checked: kernelmode_fixup_or_oops, which oopses when there is no entry]

### §4b Locking discipline

The acquisition order below is the part of this section most likely to be wrong, because it is the part that cannot be worked out from one file. It is the first thing to verify against a tree.

What protects each thing this mechanism touches:

| Thing | Protected by |
|---|---|
| the VMA tree in `mm_struct` [page-fault-R8] | `mmap_lock (r)` for a lookup, `mmap_lock (w)` to change it |
| one VMA, on the fast path [page-fault-R5] | `rcu` for the lookup, then a per VMA lock for the fault |
| the page table entry being installed | the page table lock for the level being written |
| the folio content while it is being copied | `folio_lock` |
| the fault flags and address in `vm_fault` [page-fault-R9] | `owner`, one fault owns its own state |
| the fault counters [page-fault-R27] | `atomic` |
| the reference on an installed folio | `caller-ref` until the entry is written, then the mapping owns it |

Acquisition order, written as a chain with `>` meaning taken before:

`mmap_lock > i_mmap_lock > anon_vma > folio_lock > pte lock`

Three rules that fall out of that chain and are worth stating on their own:

- The page table lock is the innermost lock this mechanism takes. Nothing sleeps while holding it, and a path that needs to sleep drops it, sleeps, retakes it and rechecks.
- The per VMA lock is not in the chain because it is an alternative to the start of it. A fault holds either the per VMA lock or the mmap lock, never both.
- `FAULT_FLAG_ALLOW_RETRY` [page-fault-R10] exists so that a fault which needs to wait on storage can drop the mmap lock before waiting. Without it, one thread waiting on a disk read would block every `mmap` in the process for the duration.

### §4c Execution context

Two entry points, and they have different answers, which is the whole reason this subsection exists.

`exc_page_fault` [page-fault-R1] runs in whatever context the faulting instruction was in, because it is a trap and not a call.

| Context | Allowed | What it may do |
|---|---|---|
| `P` | yes | anything, including sleeping |
| `PP` | yes | resolve without sleeping, or take the exception table |
| `A` | yes | exception table only, a fault needing work here is a bug |
| `SI` | yes | exception table only |
| `HI` | yes | exception table only |
| `NMI` | yes | exception table only, and the machine is in a bad state either way |

`handle_mm_fault` [page-fault-R11] is a call and not a trap, so it has one answer.

| Context | Allowed | What it may do |
|---|---|---|
| `P` | yes | anything, including sleeping and allocating |
| `PP` | no | it can sleep, so it cannot be called with preemption disabled |
| `A` | no | same |
| `SI` | no | same |
| `HI` | no | same |
| `NMI` | no | same |

The `PREEMPT_RT` delta: the page table lock becomes a sleeping lock, so a path that was atomic on a mainline build is preemptible on an RT build. That removes the rule about not sleeping under the page table lock and replaces it with a different one, that the code under it must be preemptible, which is a stronger requirement than it sounds. The exception table cases are unaffected, because they never reach a lock.

## §6 Edge cases and failure modes

- **allocation-failure.** There are four allocation sites: the page table levels during the walk [page-fault-R12], the folio in the anonymous path [page-fault-R14], the copy in the copy on write path [page-fault-R16], and whatever the filesystem allocates underneath `filemap_fault` [page-fault-R18]. All four return `VM_FAULT_OOM` [page-fault-R20], and that value does not become an error code for userspace. It goes to the out of memory killer [page-fault-R26], which kills something, possibly the faulting process and possibly not.

- **concurrent-entry.** Two threads in the same address space faulting on the same address at the same time is normal and happens constantly on a threaded program's first touch of a heap. Both walk, both may allocate, and the page table lock decides which one installs. The loser frees its folio and uses the winner's, and neither notices.

- **wrong-context.** A fault taken while the kernel holds a spinlock cannot be resolved. The exception table [page-fault-R23] covers the expected cases, which are the `copy_from_user` family reaching into a user address that is not mapped. Anything else oopses. This is why the rule about not touching user memory while holding a spinlock is a rule about faults and not about locking.

- **signal.** A fault that is waiting on a disk read can be interrupted. The wait is killable rather than fully interruptible, so a fatal signal ends it and an ordinary one does not. When it does end that way the fault returns without having fixed anything, the process is on its way out, and the instruction is never retried.

- **object-freed.** The file behind a mapping can be truncated while a fault on it is in flight. The fault can have read a folio that is no longer part of the file by the time it goes to install it, which is why the install step rechecks under the page table lock [page-fault-R17] rather than trusting what it read.

- **refcount-zero.** Every folio installed into a page table holds a reference for that mapping. The dangerous window is between allocating the folio and writing the entry, where the fault holds the only reference and any early return has to drop it. A leak here is invisible until the machine runs out of memory much later.

- **boundary-cases.** An access one byte past the end of a VMA is SIGSEGV and an access on the last byte inside it is a normal fault, and the two are one address apart. A fault on the page immediately below the stack grows the stack [page-fault-R6], and a fault one page further down does not. A mapping of length zero cannot be faulted on because it cannot exist.

- **hostile-input.** The faulting address comes from the hardware and is whatever the program put in a register, so it is fully attacker controlled on any machine running untrusted code. The handler treats it as a number to look up and never as a pointer to dereference, which is the property that makes an arbitrary faulting address harmless.

- **bug-message.** Two messages come out of this path and both are worth knowing by their exact text. `BUG: unable to handle page fault for address` [page-fault-R21] is a kernel mode fault with no exception table entry, which means a kernel pointer bug and not a userspace one. `BUG: Bad page map in process` [page-fault-R22] is a page table entry pointing at something that is not a valid page, which means memory corruption that was found here rather than caused here.

## §8 Configuration and architecture dependence

Which symbols change what is written above:

- `CONFIG_PER_VMA_LOCK` removes step 6's fast path [page-fault-R5]. Without it every fault takes the mmap lock, and the concurrency described in section 4b is not there.
- `CONFIG_TRANSPARENT_HUGEPAGE` adds the pmd level answer [page-fault-R25]. Without it the walk always reaches a pte, and section 3 step 9 has one fewer exit.
- `CONFIG_SWAP` removes the swap branch of step 10 [page-fault-R15]. Without it a fault is never major for that reason, and the major fault counter moves only for file backed reads.
- `CONFIG_NUMA_BALANCING` adds a branch to the dispatch that is not in section 3 at all: an entry deliberately made not present so that a fault on it can be used to decide where the page should live.
- `CONFIG_USERFAULTFD` lets a userspace process register to handle faults on a range itself, which turns step 10 into a message to another process and a wait.
- `CONFIG_MEMCG` adds a charge against a memory control group to every allocation in section 6, and gives every one of them a second way to fail that has nothing to do with the machine being out of memory.
- `CONFIG_X86_5LEVEL` adds a level to the walk in step 9. The code is written to fold the extra level away at runtime, so the number of levels is a property of the running machine and not of the build.

Architecture dependence:

Steps 1 to 5 are entirely x86-64 and every architecture writes them differently. What is shared is the shape and not the code: read the faulting address from wherever the hardware left it, decode a reason from wherever the hardware left that, and call `handle_mm_fault`. On arm64 the address is in FAR_EL1 and the reason is in ESR_EL1, which is a richer encoding than the x86 error code, and the split between a translation fault and a permission fault is explicit in the hardware rather than inferred from a present bit.

Steps 6 onwards are architecture independent, with one exception worth naming. The page table walk in step 9 assumes a tree, and every architecture Linux supports uses one, but the number of levels and the page sizes differ, and a page table entry is a different width on a 32-bit build than on a 64-bit one.

That last point is the one that matters for this project. The pinned kernel is built for 32-bit x86 with one processor, because that is the machine the browser emulator provides. On that build there are two page table levels rather than four, `CONFIG_HIGHMEM` becomes a live concern that does not exist on 64-bit at all, and having one processor means the concurrent cases in section 6 cannot be produced. Reading this blueprint against that kernel is reading it against a machine that has fewer of these problems, which is a good way to learn the mechanism and a bad way to convince yourself you have seen all of it.

## §9 Reimplementation notes

Forced by the hardware:

- The trap itself, the faulting address register, and the requirement that the handler leave the machine able to rerun the instruction. Nothing about this is a choice.
- The page table format. The processor walks it, so its shape is decided by the processor and not by the kernel.

Forced by the syscall ABI:

- That a bad access produces SIGSEGV with a `si_addr` pointing at the faulting address. Programs handle this signal and inspect that field, so it cannot change.
- That `mmap` returns immediately and the mapping is populated later. A kernel that populated eagerly would be within its rights but would break the memory overcommit that most software has been written to assume.

Choices Linux made that another kernel could make differently:

- **Answering on the faulting thread.** Linux resolves the fault on the thread that took it, so the thread is blocked for the duration. A kernel could instead hand the fault to a service thread and let the faulting thread be descheduled explicitly. That would cost a context switch on every fault, which is far too expensive for the common minor fault, and would be much cheaper for a major fault that is going to wait on storage anyway. Splitting the two paths is a design nobody has shipped and there is no reason in principle it could not be.

- **The VMA as the unit of description.** A VMA is a range with uniform properties, and looking one up is a tree search on every fault. A kernel could describe an address space as a flat array of per page descriptors instead, which would make the lookup a single index and the memory cost enormous. Linux is at one end of that trade and Mach style memory objects are nearer the other.

- **Copy on write as the default for private mappings.** Nothing requires it. A kernel could copy eagerly at `fork` and have no copy on write faults at all, and the cost would be paid by every `fork` including the overwhelming majority that call `exec` immediately afterwards. The cost of the current choice is that a write to a private mapping can fail with out of memory long after the mapping was created, which is a failure at a point where no programmer expects one.

- **The shared zero page.** A read of untouched anonymous memory maps one global read only page. This is a pure optimisation for a common pattern, it is invisible to a correct program, and it makes the next write to that address fault a second time. A kernel could allocate on the first access of any kind and would have fewer faults and more memory in use.

- **Retry rather than sleep under the lock.** `FAULT_FLAG_ALLOW_RETRY` [page-fault-R10] is Linux choosing to unwind the whole fault and take it again rather than hold the address space lock across a disk read. The alternative is a lock that can be held while sleeping, which is what a kernel with a different locking model would use, and it moves the cost from repeated work to reduced concurrency.
