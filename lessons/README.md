# Lessons

One directory per lesson, named for its identifier. Identifiers come from the curriculum and never change, because links, graders and the claim ledger all point at them.

```
lessons/Z02/
├── build.py         # the lesson: prose and cells. The only file here you edit.
├── Z02.ipynb        # generated. What the Colab badge opens.
├── lesson.md        # generated. The prose, in blocks, each with a word cap.
├── meta.toml        # the identifier, and whether this is a draft or published
├── claims.toml      # every claim, with the evidence that backs it
├── grader.py        # what has to be true before the lesson is done
└── assets/          # diagrams, animation sources, images
```

## One source, two outputs

`build.py` is the lesson. The notebook and the markdown are both generated from it, so a paragraph exists once and the two cannot end up saying different things.

Run `just build-lessons` after an edit and `just notebooks` to check. CI runs the check, so a committed notebook that disagrees with its builder fails the build. Both outputs stay committed on purpose: a reader who clicked a Colab badge has the notebook and nothing else, and GitHub renders the markdown without running anything.

The builder is `tools/nbbuild.py`, and a lesson uses five things from it.

- `lesson.badge`, the Colab link, generated from the path the notebook is about to be written to.
- `lesson.md(text)`, a markdown cell.
- `lesson.code(source, note)`, a code cell. The note says why the cell is there and only reaches the builder.
- `lesson.block(name)`, opening one of the five blocks. The marker reaches `lesson.md`, where `lintprose` reads it to apply the word caps.
- `lesson.claim("Z02-05")`, which returns the claim's own words from `claims.toml` and records where it was made.

The last one is the rule with teeth. A claim whose evidence is something the reader can run has to be followed by a code cell, and that cell has to come before the next heading. Without the second half, any cell further down the lesson would satisfy it, and the check would pass on a lesson that proves nothing. Claims backed by a citation, and claims marked unobservable, are exempt, because there is nothing to run.

## The seven rules

Run `just notebook-rules` for the list and `just notebook-contract` to check every lesson against it. The rules are the banner first, nothing a browser cannot finish, a caption on every code cell, a widget instead of a raw print where one exists, twenty code cells at most, evidence through the box or a corpus helper, and no writing outside the scratch directory. CONTRIBUTING.md says what each one is for. The checker reads the committed notebook rather than the builder, because the notebook is the file a reader opens.

Two of them need a helper. `kxray.banner()` is the cell after the setup cell in every lesson: it prints which kernel this project pins, what Tier 0 cannot do, which backend the session got, and whether the machine running the notebook can trace anything itself. `kxray.colab.scratch("C09")` is the directory a lesson writes into, made on first use and the same path every time, so a lesson that hands the reader a C file to build does not leave it in whatever directory they started Jupyter in.

## Running a lesson in Colab

The first code cell installs the toolkit from the repository if it is not there, and finds it without installing anything if you are inside a checkout. After that, `kxray.colab.lesson_module` loads the lesson's grader, from your working copy when there is one and from the default branch otherwise, printing the URL it fetched.

Colab is a real Linux machine, so a lesson can try the real thing. `kxray.tracefs` reports what the runtime can do before the lesson asks for anything, and when tracing is not available it names which of the three preconditions is missing: the tracer built into the kernel, the tracing filesystem mounted, and root. Every lesson that needs a capture also takes a pasted one, so a reader on a locked down runtime is not stuck.

## Drafts and published lessons

`meta.toml` carries a status. A draft can say what it expects the evidence to be before that evidence exists, which is how a lesson gets written while the tooling it needs is still being built. A published lesson has to have every claim verified, and `just claims` will not let it through otherwise.

## Diagrams

A diagram is a Python file in `assets/` named `*.diagram.py`, and the `.svg` and `.excalidraw` beside it are generated by `just diagrams`. The lesson shows the SVG through `lesson.image`, which writes an absolute URL, because a relative path renders on GitHub and shows a broken image in a notebook that was fetched on its own. Open the excalidraw file when you want to drag things around, then move what you worked out back into the Python and rebuild.

Every diagram source has to define an `ALT` string describing what somebody who cannot see it would need to know. The build fails without one, which is the only version of that rule that survives a deadline.

## The blocks

A lesson is written in blocks, marked with an HTML comment so the length caps follow the writing rather than the file.

- `hook`, at most 150 words. Why anyone should care, and a question they cannot answer yet.
- `predict`. A guess the reader writes down before running anything.
- `tour`, at most 1500 words. What actually happens, with the evidence beside it.
- `experiment`. The thing they run, and the wrong answers that were tempting.
- `change`. A modification they make, and how they know it worked.

The whole file is capped at 2500 words. A lesson that will not fit is two lessons.

## The pilot

The first three lessons are the M0 pilot, and they exist to find out whether the format works before 100 more get written in it.

- `Z02`, your first trace. Written and runnable in Colab, and a draft until there is a real capture behind it.
- `S05`, the first ops plug. Written and runnable in Colab, and a draft until three citations are confirmed against a kernel tree and there is a real capture behind the last claim.
- `C09`, lockdep. Written and runnable in Colab, and a draft until three citations are confirmed against a kernel tree and somebody has built the module and read their own report.
